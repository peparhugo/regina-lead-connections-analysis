# Regina Dream/DMG question experiment design — 2026-03-29

Status: canonical experiment-design note
Purpose: define the next substantive Regina learning phase as a bounded question + DMG experiment program, using the existing Dream/DMG harness and testing three bounded questions per selected lane/route.

---

## Executive decision

Yes: the next best step is to put the current Regina state through **question batteries plus DMG-driven experiments**, using **3 bounded questions per lane/route**.

This makes sense because the immediate problem is no longer raw recovery.
It is learning which routes/lane types now produce the most decision-useful, contradiction-safe next steps under the rebuilt control plane.

---

## Why this is the right next phase

The system is now good enough to run controlled experiments again.
The open question is not “is recovery possible?” but rather:

- which question routes are highest-yield now,
- which Dream/DMG lane types help the most,
- which routes surface contradiction-safe support/useful evidence,
- and which routes still produce noise or lane leakage.

A bounded experiment matrix answers that directly.

---

## Experiment shape

### Unit of experimentation
One experiment cell =
- one lane/route pair
- three bounded questions
- one audit bundle
- one operator summary
- findings reviewed for usefulness, contradiction-safety, and next-step value

### Principle
Use the smallest experiment set that can reveal route quality differences without going unbounded.

---

## Recommended lane/route matrix for this phase

### Route family R1 — internal contradiction / control validation
Use when pressure-testing current Regina control truth or support-layer boundaries.

#### Lane 1
- `focused / validation_or_contradiction`
- target: current support-layer contradiction review and canonical boundary enforcement

#### Lane 2
- `focused / operator_decision_support`
- target: which support-layer claims should remain support-only vs promotion-ready vs demotion-worthy

### Route family R2 — external focused evidence improvement
Use when testing bounded external learning against current Regina support/control needs.

#### Lane 3
- `focused / benchmark_or_comparison`
- target: comparable public-health framing / burden-envelope handling / appendix discipline from analogous civic or risk-communication projects

#### Lane 4
- `focused / failure_diagnosis`
- target: why some support-boundary queries still retrieve generic/noisy patterns and what route-level fixes tend to work

### Route family R3 — adjacent future-option learning
Use when exploring bounded optionality without losing project ownership.

#### Lane 5
- `adjacent / transferable_methods`
- target: contradiction-aware retrieval or support-layer separation methods transferable from adjacent domains

#### Lane 6
- `adjacent / tooling_patterns`
- target: workflow/retrieval/tooling patterns that improve support-vs-canonical separation in active research systems

---

## 3-per-lane rule

For each selected lane/route pair, run exactly **3 bounded questions**.

That means an initial six-lane sweep would produce:
- **18 total questions**
- enough variation to compare route quality
- still bounded enough to audit manually

If desired, a smaller first pass can use only the first four lanes:
- **12 total questions**
- faster operator review
- lower execution cost

---

## Recommended question families by lane

### Lane 1 — focused / validation_or_contradiction
Goal: pressure-test support-layer boundaries and contradiction handling.

Question family examples:
1. Which current support-layer burden artifacts most risk being misread as canonical current-state truth?
2. What evidence in the repo supports keeping the burden appendix strictly support-only?
3. What current support-layer wording most needs demotion, caveat reinforcement, or explicit non-promotion labeling?

### Lane 2 — focused / operator_decision_support
Goal: help choose the next best post-recovery Regina moves.

Question family examples:
1. Which support-layer artifacts are safest to preserve as support-only without promotion?
2. Which support-layer claims, if strengthened, would most improve decision quality without widening the public envelope?
3. Which contradiction-review findings would most change the next active Regina lane choice?

### Lane 3 — focused / benchmark_or_comparison
Goal: compare external patterns for bounded burden/public-health framing.

Question family examples:
1. How do similar public-interest analyses separate technical appendix burden estimates from headline claims?
2. What comparison examples show conservative scenario-envelope handling without overstating certainty?
3. Which framing patterns best preserve public usefulness while preventing pseudo-precision?

### Lane 4 — focused / failure_diagnosis
Goal: learn what still causes route/query noise or leakage.

Question family examples:
1. Why do support-boundary queries still sometimes surface generic repo patterns above the intended boundary claims?
2. What retrieval/reranking fixes work best when newly promoted governance claims still compete with older generic patterns?
3. Which route-level diagnostics best distinguish indexing absence from ranking noise from prompt mismatch?

### Lane 5 — adjacent / transferable_methods
Goal: import useful contradiction-aware methods from neighboring domains.

Question family examples:
1. What methods from safety-critical documentation or evidence review systems help preserve support-vs-canonical separation?
2. What adjacent domains have strong “scenario envelope vs settled result” control patterns worth transferring?
3. Which contradiction-aware knowledge system methods best prevent support artifacts from silently becoming canonical truth?

### Lane 6 — adjacent / tooling_patterns
Goal: find workflow/tooling patterns for maintaining lane separation.

Question family examples:
1. What tooling patterns help teams maintain explicit boundary labels across canonical, support, and appendix layers?
2. Which retrieval-system patterns reduce the impact of low-signal extracted file observations?
3. What operator-facing audit patterns best show when a route is producing useful contradiction-safe learning rather than noise?

---

## Success criteria

This experiment phase is successful if it produces:
1. a route-quality comparison across lane types;
2. a clear view of which lanes generate the best next-step evidence;
3. explicit losers to downweight or stop using;
4. at least one operator-grade next-step recommendation grounded in the experiment results;
5. audit artifacts sufficient to compare later runs without re-reading everything.

---

## Failure criteria

Treat the phase as weak/failed if:
- most questions return generic noise;
- route differences are too muddy to compare;
- accepted findings do not change action quality;
- DMG suggestions widen scope instead of staying project-owned;
- support-layer boundaries get blurrier rather than clearer.

---

## Operational recommendation

### Preferred rollout
Run this in two waves.

#### Wave A — high-value first pass
Use lanes 1–4 only:
- 12 total questions
- strong immediate relevance
- enough to identify best route family quickly

#### Wave B — adjacent expansion
Add lanes 5–6 only if Wave A produces useful differentiation.

This is more disciplined than launching all six lanes blindly.
